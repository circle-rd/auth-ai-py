---
title: Resource sharing
description: Ask auth-service whether a user may use a shared resource, list what they can reach, and report the validation or loss of ownership of a resource you own.
---

auth-service lets a user or an application **own** a resource (a model, an agent, an MCP server, an SSH account, or a resource of a scheme your application defines) and **share** it with users, organisations, plans or every member of the application. The decision is always auth-service's: your code asks and obeys. Concepts and operator side: [Resource sharing](https://docs.circle-cyber.com/auth-service/docs/project/resource-sharing-final-design) in the auth-service documentation.

The calls below are the `machine.resources` client of the [machine API](/docs/reference/server-api#machineresources) and the signed-in user's `user.resources` client.

## Share from a user's session

Turn on `resource_sharing=True` in `AuthClientConfig`. The SDK then requests the
`resources:self:manage` scope and the auth-service audience at sign-in; its
access token is the user's, so the application can only act on what that user
owns or administers.

```python
from auth_ai import Audience

user = ai.for_user(user_id)
application = next(
    app for app in await user.resources.list_member_applications() if app.slug == "gine"
)

resource = await user.resources.create(
    application_id=application.id,
    scheme="gine",
    display_name="Firmware",
    locator="project-42",
)
await user.resources.request_validation(resource.id)  # or let your validator mark it

await user.resources.create_grant(
    resource.id, subject_type="user", subject_email="colleague@example.com"
)
await user.resources.create_grant(
    resource.id, subject_type="organization", subject_id=organization_id, permission="write"
)
await user.resources.share_with_application([resource.id], application_slug="chat")

for shared in await user.resources.list_accessible(scheme="gine"):
    print(shared.resource_uri, shared.permission)
```

- `create_grant` accepts a user by `subject_email` (resolved by auth-service among the
  application's active members) or by `subject_id`; an unknown address is refused like a
  non-member and creates no row.
- `permission` is `"read"` (default) or `"write"`, and `"write"` also covers `"read"`.
  `update_grant(resource_id, grant_id, permission=...)` changes the level without revoking
  the grant (`RES_014` when the scheme does not support the level, `RES_015` for an inactive
  grant).
- `subject_type="application"` shares the resource with another application, named by its
  slug in `subject_id`. A scheme an application defines is shared inside that application only.
  `share_with_application` does it for up to 100 resources in one call and returns one
  `BulkShareResult` per resource: a `grant_id`, or the refusal `code`.
- The owner may share with an organisation they belong to. Access still requires an active
  membership in the resource's application.
- `delete` removes a resource for good, with its grants (`RES_019` while the relay still
  serves the model). `revoke_grant` ends an active grant and keeps the row as history;
  `delete_grant` deletes a revoked or expired one (`RES_020` for an active grant).
  `update` and `list_grants` cover the rest of the lifecycle.
  `AuthClientConfig.resource_sharing=True` is required: without the scope the calls raise
  `TOK_004`.

## Verify resource webhooks

Set `resourceWebhookUrl` on the application in auth-service. The service then POSTs signed
events (`resource.grant.created`, `resource.grant.revoked`, `resource.grant.updated` for a
level change, and `resource.deleted`) to it. Verify before parsing:

```python
from auth_ai.server import ResourceDeletedEvent, verify_resource_event

event = verify_resource_event(request.headers, await request.body(), WEBHOOK_SECRET)
if isinstance(event, ResourceDeletedEvent):
    forget(event.resource.id)
else:
    for user_id in event.recipients.user_ids or []:
        notify(user_id)
    if event.recipients.all_members:
        notify_everyone()
```

The helper checks `X-Auth-Service-Signature` (`t=<unix>,v1=<hmac>`) over the raw body,
rejects a timestamp older than five minutes, and validates the payload shape. Deduplicate on
`event.event_id`; never treat a delivery as authorization.


## Prerequisites

- auth-service runs with `RESOURCE_SHARING_ENABLED` on, and sharing is enabled for the application that offers the resource. Without it the routes do not exist and every call raises `API_001` with `details["status"]` `404`.
- A **confidential** application, as for the rest of the machine API.
- The machine scope of what you call:

| You are | Scope | Calls |
| --- | --- | --- |
| The validator bound to a resource scheme (your application owns the scheme) | `resources:validate`, given to new confidential applications | `validate`, `invalidate` |
| An enforcement point that admits users to resources | `resources:authorize`, granted by a superadmin | `authorize`, `list_accessible` |
| A metering component that reports what a provider billed | `resources:usage:write`, granted to the platform's metering components only | `record_usage` |

Every decision is taken for the **application whose credential you use**: it sees the resources that application owns and the ones shared with it, never everything a user owns. A missing scope makes the call raise `TOK_004` with the scope in `details["scope"]`.

## Admit a user to a resource

```python
from auth_ai.server import Allowed, BearerVerifier, MachineApi

verifier = BearerVerifier(auth, audience="https://api.example.com")
machine = MachineApi(auth)

token = await verifier.verify_header(request.headers.get("authorization"))
if token.user_id is None:
    raise PermissionError("A user token is required")

decision = await machine.resources.authorize(
    subject_id=token.user_id,  # the verified `sub`
    actor_client_id=token.client_id,  # the verified `azp`, kept for audit
    resource_uri="gine://project-42",
    audience="https://api.example.com",
    permission="write",  # `read` by default
    request_id=request_id,
    source="external",
)

if not isinstance(decision, Allowed):
    raise PermissionError("Forbidden")
print(decision.access_kind, decision.permission)  # "owner" or "grant"; "read" or "write"
```

- **Take `subject_id` and `audience` from a token you verified**, never from a request body: auth-service trusts them as they come. `actor_client_id` only labels the access log; the calling application is your machine credential.
- **Fail closed.** Only an `Allowed` answer is an admission. A denial carries no reason, so it cannot be used to probe which resources exist, and an `authorize` that raises (`API_001`, `API_002`, a timeout) is a denial too.
- **`write` covers `read`.** Ask for the level the request needs: a `read` grant is refused when you ask for `write`. The answer carries the level the user holds, so an interface can show or hide actions without trying them.
- Ask for every request that needs it: the answer reflects revocations, bans and membership changes at once, so do not keep it longer than the request.

## List what a user can reach

```python
for resource in await machine.resources.list_accessible("user-sub", scheme="llm"):
    print(resource.resource_uri, resource.access_kind, resource.permission)
```

The list holds what your application owns and what was shared with it. Use it to filter what you show, and call `authorize` for the decision itself.

## Validate a resource you own

When an owner asks to validate a resource of a scheme your application defines, auth-service marks it pending and waits for your answer. You prove the ownership your own way (the project belongs to the caller, the object exists), then report:

```python
await machine.resources.validate(resource_id, result="validated", evidence={"checkedBy": "my-app"})

await machine.resources.validate(
    resource_id,
    result="validation_failed",
    reason="This project belongs to another account",
)
```

`reason` is shown to the owner. `evidence` is stored with the resource: never put a secret in it.

When ownership is lost later (the project was deleted, a host key changed), disable the resource so access stops at once:

```python
await machine.resources.invalidate(resource_id, "project-deleted")
```

Only the client bound to the resource's scheme may call `validate` and `invalidate`; another client gets `API_001` with `details["apiCode"]` `AUTH_011`.

## Report the usage of a resource

A metering component reports what a provider billed for a resource. auth-service owns accounting; this is the only write and reading stays with it.

```python
from datetime import UTC, datetime

receipt = await machine.resources.record_usage(
    decision_id=decision.decision_id,  # from the `authorize` that admitted the request
    started_at=started_at,  # when that request started
    resource_id=resource_id,
    resource_uri="llm://acme/gpt-x",
    request_id=event_id,  # 64 lowercase hex characters, stable per event
    occurred_at=datetime.now(UTC),
    usage_source="provider",
    cost_usd="0.0042",
    prompt_tokens=120,
    completion_tokens=30,
    total_tokens=150,
)
```

Replaying the same event is safe: `receipt.replayed` is `True`. Use `usage_source="unsupported"` with no cost and no tokens when the provider reports nothing. The `decision_id` names the person and the application, so a usage event cannot claim another one; it lives 60 seconds and only the client that obtained it may present it. A payload that conflicts with the stored event is refused with `RES_012`, a caller with no access to the resource with `RES_011`, and a decision that is expired, forged or issued to another client with `RES_016` (all `API_001`).

## Errors

| Situation | Error |
| --- | --- |
| Invalid input (id not a UUID, empty subject, reason too long) | `CFG_001`, before any request |
| Scope not granted | `TOK_004`, `details["scope"]` |
| auth-service refused (`AUTH_011`, `RES_001`, `RES_004`…) | `API_001`, `details["status"]` and `details["apiCode"]` |
| Unexpected answer | `API_002` |
