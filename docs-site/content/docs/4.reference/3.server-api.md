Everything below is exported from `auth_ai.server`. It needs no web framework.

## Bearer verification

`BearerVerifier(auth, *, audience)` verifies JWT access tokens minted for **your API**. `auth` is an `AuthClient`; `audience` must be a URL (otherwise `CFG_001`) and must appear in the token's `aud`. Opaque tokens are refused.

| Member | Description |
| --- | --- |
| `verify(token) -> VerifiedAccessToken` | Verifies a raw JWT: signature, issuer, audience and expiry, then that it is bound to a client (`azp`). Failures are `TOK_001`. |
| `verify_header(authorization) -> VerifiedAccessToken` | Same, from the value of an `Authorization: Bearer …` header (`str \| None`). A missing or malformed header raises `TOK_003`. |

Related functions:

| Function | Description |
| --- | --- |
| `extract_bearer_token(authorization) -> str` | Returns the token of a bearer `Authorization` header, or raises `TOK_003`. |
| `require_scopes(token, *required)` | Raises `TOK_004` (with `details["missing"]`) unless the `VerifiedAccessToken` carries every listed scope. |

`VerifiedAccessToken` is a frozen dataclass:

| Field | Description |
| --- | --- |
| `user_id` | The end user's `sub`, or `None` for a `client_credentials` token (where `sub` is the client id itself). |
| `client_id` | The OAuth client the token was issued to (`azp`). |
| `scopes` | `tuple[str, ...]` of the granted scopes. |
| `audiences` | `tuple[str, ...]` of the `aud` values. |
| `claims` | The `AccessTokenClaims`. |

See [Protect an API](/docs/guides/backend/protect-an-api) for a complete example.

## Protected-resource metadata

| Function | Description |
| --- | --- |
| `protected_resource_metadata(auth, *, resource, scopes_supported=None) -> dict[str, object]` | The RFC 9728 document: `resource`, `authorization_servers` (the issuer), `bearer_methods_supported` (`["header"]`) and, when given, `scopes_supported`. |
| `protected_resource_metadata_path(resource) -> str` | Where to serve it: `/.well-known/oauth-protected-resource` followed by the path of `resource`. |
| `bearer_challenge(resource_metadata_url, *, error=None, scope=None) -> str` | The value of the `WWW-Authenticate` header of a `401` or `403`. `error` is `"invalid_token"` or `"insufficient_scope"`. Raises `CFG_001` for a value containing `"`, `\`, CR or LF. |

## Back-channel logout

`BackchannelLogoutHandler(*, auth, on_logout, replay_store=None, on_error=None)` handles the endpoint auth-service calls when a user signs out. `AuthHandlers` mounts one at `/backchannel-logout` for you; build your own only when you do not use the sign-in handlers.

It is a callable: `await handler(request)` takes a `WebRequest` and returns a `WebResponse`. It is called without cookies or credentials, so mount it outside any session or CSRF protection.

| Part | Description |
| --- | --- |
| `on_logout` | `Callable[[BackchannelLogoutEvent], Awaitable[None] \| None]`. Called with a `BackchannelLogoutEvent` (`sid`, `sub`): end every local session whose stored `sid` equals this one. |
| `replay_store` | A `ReplayStore`, defaulting to `MemoryReplayStore()`. Share it across replicas. |
| `on_error` | Receives every rejected token and failed callback: the response carries no detail. |

Answers:

| Status | When |
| --- | --- |
| `200` | The logout token is valid and `on_logout` succeeded. |
| `400` with `{"error": "invalid_request"}` | The content type is not `application/x-www-form-urlencoded`, the body is larger than 16 KiB, `logout_token` is missing, or the token is invalid or replayed. |
| `500` with `{"error": "server_error"}` | `on_logout` failed. |
| `405` with `Allow: POST` | Any other method. |

`verify_logout_token(auth, token, replay_store) -> LogoutTokenClaims` is the verifier behind it. It requires a `logout+jwt` for your client id with the back-channel logout event, a `jti`, a `sid` and a `sub`, no `nonce`, a lifetime of at most 600 seconds and an `iat` not in the future, and claims the `jti` once. Failures are `TOK_001`. `LogoutTokenClaims` has `sid`, `sub`, `jti`, `iat` and `exp`.

`ReplayStore` is a protocol with one method, `claim(jti, expires_at) -> bool`: `True` the first time, `False` on a replay. See [Implement the stores](/docs/guides/backend/custom-stores).

## Resource webhooks

`verify_resource_event(headers, body, secret, *, tolerance_seconds=300, now=None) -> ResourceEvent` verifies the callback auth-service sends to an application's `resourceWebhookUrl`. `body` is the raw bytes (or text) before JSON parsing; `headers` is any case-insensitive mapping. It expects `X-Auth-Service-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256>` over `<t>.<raw body>`, rejects a timestamp outside the window (`REQ_001`), and validates the payload. `ResourceEvent` is a union of `ResourceGrantEvent` and `ResourceDeletedEvent`, discriminated on `type`. Every event has `event_id`, `type`, `occurred_at`, `application` and `resource` (`id`, `uri`, `scheme`, `display_name`, `owner_type`, and `owner_id` only for the application that owns the resource). `resource.grant.created`, `resource.grant.revoked` and `resource.grant.updated` (a level change) are a `ResourceGrantEvent`: `resource.status`, `grant` (`id`, `subject_type`, `subject_id`, `permission`, `previous_permission`, `expires_at`) and `recipients`; `recipients.user_ids` is `None` with `recipients.all_members=True` when the audience cannot be enumerated. `resource.deleted` is a `ResourceDeletedEvent` and carries the resource only. Deduplicate on `event_id`; a delivery is a notification, never an authorization decision.

## `MachineApi`

`MachineApi(auth)` calls the auth-service REST API **as your application**, with `client_credentials` tokens minted from its own secret. It raises `CFG_001` without a `client_secret`. The scopes `billing:read`, `consumption:read`, `consumption:write` and `resources:validate` are granted to new confidential applications; `resources:authorize` is a platform scope that only a superadmin grants. A refused scope raises `TOK_004` with `details["scope"]`.

It has three members, `billing`, `consumption` and `resources`. See [Billing and consumption](/docs/guides/ai-and-billing/billing-and-consumption) and [Resource sharing](/docs/guides/ai-and-billing/resource-sharing).

### `machine.billing`

| Method | Returns | Description |
| --- | --- | --- |
| `get_subscription(user_id)` | `SubscriptionView \| None` | `None` when the user has no subscription. Fields: `plan` (`id`, `name`), `is_active`, `expires_at`, `stripe_status`, `current_period_start`, `current_period_end`, `cancel_at_period_end`, `canceled_at`. |
| `get_usage(user_id)` | `UsageView` | `period_start` and `features`: each has `feature_key`, `unit`, `usage_limit` (`-1` is unlimited), `used` and `remaining` (`None` when unlimited). |
| `list_invoices(user_id, *, limit=None, cursor=None)` | `InvoicePage` | `items` (`InvoiceView`) and `next_cursor`. Newest first; `limit` is 1 to 100. |

An `InvoiceView` has `id`, `status`, `billing_reason`, `currency`, `amount_due`, `amount_paid`, `amount_remaining`, `period_start`, `period_end`, `created_at`, `hosted_invoice_url` and `invoice_pdf`.

### `machine.consumption`

| Method | Returns | Description |
| --- | --- | --- |
| `report(user_id, key, value, *, idempotency_key=None)` | `ConsumptionResult` | Reports `value` units of `key`. `aggregate` is the running total (`key`, `total` as a decimal string) and `metered` is `True` when the key prices a metered feature. |
| `list_aggregates(user_id)` | `list[ConsumptionAggregate]` | Every running total of a user: `key`, `total` and `updated_at`. |
| `get_aggregate(user_id, key)` | `ConsumptionAggregate` | One running total. Raises `API_001` with `details["apiCode"]` `CONS_003` when the key was never reported. |

`report` validates before sending and raises `CFG_001` for an empty `user_id`, a `key` that is not 1 to 64 characters of `a-zA-Z0-9.`, a non-finite or non-numeric `value` (a `bool` is refused), or an `idempotency_key` that is empty or longer than 200 characters once trimmed.

### `machine.resources`

Resource sharing for an adapter service or an application that owns a resource scheme. auth-service stays the decision point; these calls ask it. They need an auth-service with `RESOURCE_SHARING_ENABLED` on: otherwise the routes do not exist and the call raises `API_001` (`details["status"]` `404`). See [Resource sharing](/docs/guides/ai-and-billing/resource-sharing).

| Method | Scope | Returns | Description |
| --- | --- | --- | --- |
| `authorize(*, subject_id, resource_uri, audience, actor_client_id=None, permission=None, request_id=None, source=None)` | `resources:authorize` | `Allowed \| Denied` | Whether a user may use a resource through your application. `Allowed` has `decision_id`, `expires_at`, `resource_id`, `resource_uri`, `application_slug`, `owner_type`, `owner_id` (only when your application owns the resource), `access_kind` (`owner` or `grant`) and `permission` (`read` or `write`, the level the user holds); `Denied` carries nothing else. `permission` in the call is the level the request needs, `read` by default. `actor_client_id` is the client the end user came through, recorded for audit only. |
| `list_accessible(subject_id, *, scheme=None)` | `resources:authorize` | `list[AccessibleResource]` | Every validated resource the user may use through your application, each with its `permission`. A listing filter, never an admission. |
| `validate(resource_id, *, result, reason=None, evidence=None)` | `resources:validate` | `ResourceState` | The outcome of your ownership check: `result` is `validated` or `validation_failed`. `ResourceState` has `id`, `uri`, `status` and `validation_error`. |
| `invalidate(resource_id, reason)` | `resources:validate` | `ResourceState` | Disables a resource whose ownership was lost. |
| `record_usage(*, decision_id, started_at, resource_id, resource_uri, request_id, occurred_at, usage_source, cost_usd=None, prompt_tokens=None, completion_tokens=None, total_tokens=None)` | `resources:usage:write` | `UsageReceipt` | Reports what a provider billed for a resource. `decision_id` comes from the admitting `authorize`; `started_at` is when that request started. `UsageReceipt` has `usage` (`id`, `resource_id`, `request_id`, `occurred_at`) and `replayed`. |

Every input is validated before anything is sent and raises `CFG_001` otherwise: `resource_id` is a UUID, `resource_uri` is 3 to 512 characters, `scheme` matches `^[a-z][a-z0-9]{0,49}$`, `permission` is `read` or `write`, `reason` is at most 500 characters after trimming (non-empty for `invalidate`). An `authorize` answer that is neither a known `deny` nor a complete `allow` raises `API_002`: treat every raised error as a denial. `validate` and `invalidate` are refused with `API_001` (`details["apiCode"]` `AUTH_011`) when your client is not the validator bound to the resource's scheme.

`authorize` has no `client_id`: the application asking is your machine credential.

`record_usage` is the only accounting write the SDK exposes: auth-service owns accounting and the reads stay with it. It needs `resources:usage:write`, which is granted to the platform's metering components only, never by default. `decision_id` is short-lived (60 seconds, never past the user's token) and names the person and the application, so a usage event cannot claim another one: only the client that obtained a decision may present it, and `started_at` must fall within its lifetime (`RES_016` otherwise). `request_id` is the event's trusted identifier (64 lowercase hex characters) and makes the call idempotent: a replay answers `replayed=True`. A payload that conflicts with the stored event raises `API_001` with `details["apiCode"]` `RES_012`; a caller with no access to the resource gets `RES_011`. It raises `CFG_001` before any request for a naive or out-of-window `occurred_at` (five minutes ahead, 30 days back), a `cost_usd` that is not a plain decimal or is missing for `provider` usage, or any cost or token on `unsupported` usage.
